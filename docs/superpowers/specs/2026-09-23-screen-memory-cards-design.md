# 화면 기억 카드 — 설계 (2026-09-23)

## 왜

텍스트 수집(접근성 트리 앞 300자, 전체 화면 OCR)은 사이드바·메뉴·옆 창 글자로 오염되어 업무 판정의 근거가 약했다. 예: Chrome 에서 수학 페이지를 보던 행에 옆 VS Code 창의 OCR 글자가 붙어 캡스톤 업무로 판정됨.

스파이크(실제 스크린샷 11장, gpt-5.6-luna, Codex 백엔드) 결과:

| 방식 | 시간 | 입력 토큰 | 내용 |
|---|---|---|---|
| 한 장씩, detail auto | 장당 4~9초 | 장당 ~2,200 (이미지 ~1,200) | 좋음 |
| 11장 한 번에, auto | 30초 | 16,069 | 좋음, 흐름 덕에 판정 하나 개선 |
| 한 장씩, detail low | 장당 4초 | 장당 ~1,200 | 나쁨 (없는 내용 지어냄) |

- 화면 내용은 정확하고 검색 가능하게 나온다 (강의자료 제목·날짜·목차, 코드 이름, git 메시지).
- 창 제목과 실제 문서가 어긋난 행을 화면으로 바로잡는다.
- "왜 봤나"(업무)는 화면 한 장으로는 흔들린다 → 판정은 카드들의 시간순 흐름으로 따로 한다.

## 사용자 결정

- 이미지를 ChatGPT(luna)로 보내도 된다. 보내는 경우를 정확히 정한다.
- 기억 검색은 시간·업무·내용 전부.

## 구조: 두 단계

1. **화면 → 카드** (멀티모달, 사실만): 무엇을 했나, 화면 내용, 화면 종류. 업무 판정 없음.
2. **카드 흐름 → 업무 배정** (텍스트, 지금의 `assign_rows`): 행의 근거로 `text:` 대신 카드(`screen:`)를 넣는다. 카드가 없는 행은 지금처럼.

## 1. 찍기 · 묶기 · 보내기

찍기 (수집기, 로컬)
- 화면이 바뀌면 1.5초 뒤 한 장. 같은 화면에 머무는 동안은 60초마다 한 장.
- 활성 창(1600px). 찍는 동안 창이 바뀌면 버림. 제외 앱·비공개 창은 안 찍음.
- 사진마다 차이 해시(64비트)를 원시 행에 기록 (`observations.screen_hash`).

묶기 (배치마다, `KeyframeSelector`)
- 배치의 행(압축된 ActivityRow)마다 그 행의 사진들을 모은다. 해시 거리 ≤ 10 이면 같은 화면으로 묶는다.
- 묶음의 머문 시간 = 사진이 속한 행의 체류를 그 행의 사진 수로 나눠 합한 것.
- 대표 = 묶음에서 시간상 가운데 사진.

보내기
- 머문 시간 5초 이상인 묶음만 (이미지 예산 규칙이지 업무 기준이 아니다. 5초 미만 행도 제목·주소로 판정된다).
- 한 호출에 최대 12장, 넘으면 오래 머문 순. detail auto.
- 최근 24시간에 해시 거리 ≤ 10 인 카드가 있으면 다시 보내지 않고 그 카드를 연결한다.
- 제외: 잠금 화면·시스템 화면·WorkGraph 자신(`contentlessBundles`), 빈 탭·로그인(`TransientPages`), 제외 앱.

## 2. 카드

필드: 시작·끝 시각, 해시, 스크린샷 경로, 앱, 창 제목, 주소·파일, 무엇을 했나(한 문장. 대화 화면은 상대와 앱만, 단어는 해석하지 않음), 화면 내용(2~6줄, 대화는 최근 메시지 12줄까지 원문 인용), 화면 종류(document / code / web / ai_chat / message / video / tool / none), 이름 붙은 것들(`entities` JSON: documents, people, code, errors, numbers, links).

저장
- `screen_cards` 표. 원시 행에 `card_id`.
- `screen_cards_fts` (FTS5, trigram 토크나이저): 한국어 부분 문자열 검색.
- 카드는 그래프 노드가 아니다. 스크린샷이 지워져도 카드는 남는다.

## 3. 업무 배정이 카드를 쓰는 방식

- 행에 카드가 있으면 프롬프트에 `screen: 무엇을 했나 / 내용 줄` 을 붙이고 `text:` 는 뺀다. 같은 카드가 여러 행에 걸치면 처음 한 번만 전문, 이후는 `screen: (위 카드 #n 과 같음)`.
- 첫 줄은 카드 모델의 해석이고 근거는 인용 줄이다 (2026-10-02). 대화 카드는 최근 메시지 뒤에서 12줄, 그 밖은 앞에서 6줄.
- 카드가 없는 행은 지금처럼 `text:`.
- 판정 규칙(목표 / 이탈 / 없음, 자료 여부, reason)은 그대로.

## 4. 검색은 나중에 (이번 범위 아님)

사용자 결정: 이번 일은 검색 기능이 아니라 검색을 위한 데이터 저장의 고도화다. 기억 기반 검색은 카드가 잘 정리돼 있으면 LLM 이 카드를 읽어 답하면 된다. 그래서 카드를 검색하기 좋게 구조화해 쌓는다.

- 카드에 이름 붙은 것들(`entities`: 문서·파일, 사람, 코드 이름, 에러, 수치, 링크)을 따로 담는다.
- FTS5 trigram 색인은 저장 쪽 준비로 둔다 (나중에 LLM 이 후보 카드를 뽑을 때 쓴다). 검색 UI·질문 답변은 만들지 않는다.

## 비용

어제 12~20시 실측: 5초 이상 머문 서로 다른 화면 시간당 ~22개. 스크롤 변화 포함 시간당 25~35장 → 이미지 입력 시간당 4~5만 토큰, 호출 3~4번. 설정에서 끌 수 있다("화면 이해").

## 하지 않는 것

- 앞 창 잘라내기 (스파이크에서 앞 창 이름을 주면 충분했다)
- 로컬 비전 모델, 임베딩
- 카드 단계에서의 업무 판정
