# 업무 분야(테마)와 업무 종류 정리 설계

## 배경

- 10/2 회의 결정: 업무 위에 상위 분류(테마) 클래스를 하나 더 둔다. 예: 취업 준비 > 회사별 지원서 작성. 업무 단위 자체는 지금이 맞다. 상위 분류의 기준은 미결로 남았다.
- 3단계 판정 설계서는 상위 클래스를 "다음 설계에서 ③에 추가한다"고 미뤘다. 이 설계는 ③이 아니라 따로 단계를 둔다 (아래 "테마 단계").
- 지금 업무 종류(TaskType)로는 지원·신청·확인 같은 처리 업무와 면접 준비를 담지 못한다. 실제 업무 13개 중 3개가 '기타', 2개가 맞지 않는 종류(혜택 신청 → 시장조사, 면접 준비 → 복습)다.

## 목표

- 업무마다 넓은 분야 하나가 붙어, 흩어진 업무가 분야 아래 모여 보인다.
- 처리 업무와 면접 준비가 맞는 종류를 받는다.
- 한 번 붙은 분야는 실행마다 흔들리지 않는다.

## 온톨로지

```
분야(Theme) ◀─PART_OF─ 업무(Task) ─INSTANCE_OF─▶ 업무 종류(TaskType)
 취업 준비      현대오토에버 신입 채용 과제테스트 지원      신청·지원
```

- 클래스 `Theme`(분야): 업무 위의 넓은 분야. 인스턴스는 사용자마다 다르다.
- 관계 `Task —PART_OF→ Theme`: 업무당 하나. 관계 정의(RelationSchema)에 추가하고 표준은 `dcterms:isPartOf`.
- 기본 분야(코드): 학업, 취업 준비, 프로젝트, 직장 업무, 생활 행정, 자기계발. 맞는 분야가 없을 때만 새 분야를 만든다. 분야 노드는 기본 분야를 포함해 사용자당 최대 20개(Jev 선택지 제한과 같음).
- 분야 노드는 업무가 처음 들어갈 때 만들고, 업무가 하나도 없으면 지운다. 키는 공백을 정리한 이름이다. 이름을 비교할 때는 공백과 대소문자를 무시해, 거의 같은 이름은 있는 분야를 쓴다.
- 업무 종류 추가: 행정처리 ⊃ 신청·지원, 일정·공지확인 / 학습 ⊃ 면접·시험준비. 고를 수 있는 종류는 11개에서 14개.
- 업무 종류 목록에 판(`TBox.version` = 2)을 둔다. 업무를 만들 때 그 판을 업무에 기록하고, 판이 없거나 옛 판인 업무는 테마 단계가 종류도 다시 붙인다. 기존 업무는 판이 없으므로 첫 실행 때 한 번 다시 붙는다.
- 두 축: 분야는 "무엇을 위해", 종류는 "어떤 활동"이다. 예: "AI SCM 직무 면접 기술 질문 및 PT 준비" → 분야 취업 준비, 종류 면접·시험준비.

## 테마 단계

```
정리(①②③) → 새 업무 생김 → 업무 합치기 → 테마 단계
앱 시작 → 테마 단계 (처음 한 번은 기존 업무 전부: 분야 + 종류)
```

- 언제: (1) 정리에서 새 업무가 생겼을 때 업무 합치기 바로 뒤, (2) 앱을 시작할 때. 대상이 없으면 호출하지 않는다. 숨은 설정(`themes`)이 켜져 있을 때만 돌고, 기본은 꺼져 있다 (아래 측정 결과).
- 대상: 활성 업무 중 분야가 없는 것, 또는 종류의 판이 없거나 옛 판인 것. 분야가 이미 있는 업무는 종류만 묻는다.
- 입력 (호출 한 번):
  - 대상 업무마다 id, 제목, 목표, 지금 종류, 최근 작업.
  - THEMES: 있는 분야와 거기 속한 업무 제목, 아직 쓰지 않은 기본 분야, 남은 자리 수(20 − 있는 분야 수). 아직 쓰지 않은 기본 분야를 고르는 것도 자리를 쓴다.
  - TASK_TYPES: 종류를 다시 붙일 업무가 있을 때만.
- 도구 `assign_themes`: `tasks[{id, theme?, new_theme?, task_type?}]`. `theme` 은 분야가 없는 업무에만, `task_type` 은 종류를 다시 붙일 업무에만.
- 판정 규칙 (예시 없이 일반 규칙만):
  - 업무의 목표가 속한 넓은 분야를 고른다. 맞는 분야가 있으면 그것을 쓴다.
  - 새 분야는 어디에도 맞지 않을 때만, 서로 다른 여러 목표를 담을 수 있는 넓은 분야로 만든다. 목표 하나, 회사 하나, 과목 하나, 프로젝트 하나는 분야가 아니다.
  - 자리가 없으면 가장 가까운 분야를 고른다.
  - 이름은 짧은 한국어 명사구.
- 반영: 분야 노드를 만들거나 다시 쓰고 PART_OF 로 잇는다. `task_type` 이 오면 INSTANCE_OF 를 바꾸고 판과 이전 종류(`previous_type`)를 기록한다. 업무의 갱신 시각은 바꾸지 않고, 새 연결은 업무의 마지막 활동 시각으로 남긴다 (옛 업무가 최근 활동처럼 보이지 않게).
- 받아들이지 않는 답: 대상에 없는 id, 자리를 넘는 분야(기본 분야 포함), 빈 이름, 목록에 없는 종류, 분야가 이미 있는 업무의 분야 답. 그 업무는 그대로 두고 다음 기회에 다시 묻는다.
- 한 번 붙은 분야는 이 단계가 바꾸지 않는다. 옮기는 것은 나중에 화면에서 사용자가 한다.
- 실패: 호출이 실패해도 정리 결과는 그대로다. 로그에 한 줄 남긴다.
- 업무 합치기: 남는 업무의 분야를 유지하고, 남는 업무에 분야가 없으면 사라지는 업무의 분야를 받는다.
- 업무 외로 돌리기: 그 업무를 분야에서 뺀다.
- 빈 분야는 지운다.
- 판정 방식(한 번 호출·3단계)과 상관없이 돈다.

## 보이는 곳과 도구

- 그래프 뷰: 라벨 `Theme`, 이름 "분야", 새 색, 필터에 추가. 분야는 거기 속한 업무 중 가장 최근 것만큼 최근으로 보내, 오늘·7일 보기에서도 업무와 함께 보인다.
- `wgctl themes`: 분야별 업무 목록.
- `wgctl assign-themes [--retype] [--dry-run]`: 테마 단계를 CLI 로 돌린다 (데모 DB 검증용).
- `wgctl set-theme TASK_ID (분야이름 | --clear)`: 업무의 분야를 바꾸거나 뺀다 (화면이 생기기 전까지의 되돌리기).
- RDF 내보내기: `wg:Theme` 클래스, 업무→분야 `dcterms:isPartOf`.

## 확인

- 정답 세트: 지금 업무 13개의 분야·종류. 제안을 사용자가 고쳐 확정하고, 저장소 밖 `eval/themes-gold.json` 에 둔다.
- `wgctl theme-eval`: 업무 13개(제목·목표·최근 작업)를 빈 그래프에 옮겨 테마 단계를 처음부터 두 번 돌리고 정답과 비교한다 (실제 DB 에 기록하지 않음).
- 성공 기준: 분야 12/13 이상, 두 번의 결과가 다른 업무 1개 이하, 새로 만든 분야 2개 이하, 종류 11/13 이상.
- 테스트 (가짜 LLM):
  - 기본 분야를 다시 쓴다. 새 분야를 만들고, 20개 상한을 넘는 새 분야는 받지 않는다.
  - 분야가 이미 있고 판이 지금인 업무는 보내지 않는다. 옛 판 업무는 종류까지 다시 붙고 판이 기록된다.
  - 받아들이지 않는 답(모르는 id, 빈 이름, 목록에 없는 종류)은 그 업무만 건너뛴다.
  - 업무 합치기·업무 외 처리 뒤 분야를 정리하고 빈 분야를 지운다.
  - 테마 단계가 실패해도 정리 결과는 그대로다.
  - 그래프 재구성 뒤에도 업무→분야 관계가 남는다.

결정: 기준 미달 — 분야 9/13 (기준 12/13). 종류·새 분야·흔들림은 기준을 넘었다. 틀린 분야 넷 중 셋은 업무 기록(제목·목표·최근 작업)에 무엇을 위한 조사인지가 없어 기록만으로는 정할 수 없고, 하나는 과목의 팀 프로젝트가 학업과 프로젝트에 다 걸치는 경우다. 프롬프트에 예시를 넣어 맞추지 않았다.

그래서 테마 단계는 숨은 설정(`defaults write com.capstone.workgraph themes -bool true`)으로 켜고 기본은 꺼 둔다. 켤지는 사용자가 정한다. 틀린 분야는 `wgctl set-theme` 으로 고치고, 다시 붙인 종류는 `previous_type` 으로 되돌릴 수 있다.
