# 3단계 판정 파이프라인 (LangGraph) — 설계 (2026-10-05)

## 왜

목적은 업무 배정 정확도다 (사용자 결정).

정답 세트(2026-10-04~05, 664행, 사람이 확정)로 잰 근거:
- 업무 외 기준(취미·오락)과 계정 관리 기준을 고친 뒤, 지금의 한 번 호출로 91~95%.
- 남은 오답은 실행할 때마다 뒤집히는 행에 몰려 있다. 대부분 "업무냐 아니냐" 판단이다 (게임 리그, 도구 계정 화면, 몇 초 스친 행).
- 같은 배치를 다시 돌리기만 해도 판정이 꽤 달라진다 (정답 세트를 고치기 전 기준, KFPL 외 행의 약 20%). 한 호출에 96행까지 들어간다.
- "어느 업무인지"는 거의 맞힌다 (업무 행 148개 중 145개).

그래서 판단을 종류별로 쪼개, 호출마다 단순한 판단 하나만 하게 한다.

## 사용자 결정

- 판단을 쪼갠 3단계: ① 업무 여부 → ② 업무 대입 → ③ 클래스 부여.
- 단계 연결에 LangGraph를 쓴다.
- 앱을 바꾸기 전에 정답 세트로 지금 방식과 비교한다.

## 흐름

```
준비 → ① 업무 여부 ─(빠진 행이 있고 재시도 전) → ① (빠진 행만)
                    ├─(업무 행 없음) → 저장
                    └→ ② 업무 대입 ─(빠진 행이 있고 재시도 전) → ② (빠진 행만)
                                     └→ ③ 클래스 부여 → 저장
```

- **준비** (지금 코드 그대로, 그래프 밖): 행 압축(`EventCompressor`), 화면 카드(`makeCards`), 후보 업무(`openTasks(limit: 40, since: 7일 전)`).
- **저장**: 세 단계 결과를 합쳐 지금과 같은 `AssignmentPatch`를 만들고 `AssignmentApplier.apply(requireComplete: true)`에 넘긴다. 그래프·세션·자료·주제 반영과 업무 합치기(`TaskMerger`)는 바뀌지 않는다.
- 행 번호: 모든 단계가 원래 행 번호를 쓴다. ②·③은 일부 행만 받지만 번호는 그대로다.
- 호출 수: 배치당 3번. 업무 행이 없으면 1번. 빠진 행 재시도가 있으면 그 단계가 1번 늘어난다. 화면 카드 호출(새 화면이 있을 때)과 업무 합치기 호출(새 업무가 생겼을 때)은 지금처럼 따로 붙는다.
- LangChain 은 쓰지 않는다. LLM 호출은 지금의 클라이언트(ChatGPT 로그인, 함수 호출, 이미지 입력)를 그대로 쓰고, LangGraph 는 단계를 잇는 데만 쓴다.

## 단계별 입력과 출력

### ① 업무 여부 — 도구 `classify_rows`
- 입력: 모든 행 (지금과 같은 행 줄 + `screen:`/`text:`), 후보 업무의 id·제목·목표 한 줄.
- 출력: `rows[{rows: "5-12", kind: "work" | "off" | "none", reason}]`. 모든 행을 정확히 한 번.
- 규칙 (지금 프롬프트에서 옮김): 없음 / 업무 외 / 업무의 정의, 취미·오락은 목표가 아님, 목표에 쓰는 서비스의 계정·로그인·구독·결제 관리는 그 목표의 일, 카드 첫 줄은 해석이고 근거는 인용, 앱 이름이 Sillog 인 창만 없음, 행은 내용으로 판단(이웃 행 때문이 아님). 애매하면 work.

### ② 업무 대입 — 도구 `assign_tasks` (work 행이 있을 때만)
- 입력: work 행만, 후보 업무 전체 (지금과 같은 줄: 목표, 주제, 최근 한 일, 최근 자료).
- 출력: `tasks[{ref, match: "existing" | "new", id?, title?, goal?}]`, `rows[{rows, task: ref | "off", reason}]`. work 행을 모두 정확히 한 번. `"off"` 는 어느 목표에도 맞지 않음. 받지 않은 행 번호가 범위에 섞이면 무시한다. 다시 물을 때 새로 정의한 ref 는 앞 시도의 ref 와 겹치지 않게 접두어를 붙인다.
- 규칙 (지금 프롬프트에서 옮김): 업무 = 목표, 기존 업무 재사용 우선, 새 업무의 제목·목표 규칙, `off` 는 업무가 아님, 분류 이름뿐인 제목 금지.

### ③ 클래스 부여 — 도구 `describe_work` (업무 행이 있을 때만)
- 입력: TASK_TYPES, 업무별로 묶은 행 (업무 ref·제목·목표 + 그 업무에 배정된 행, 새 업무는 NEW 표시).
- 출력: `resources[{rows, resource: bool}]` (업무 행 모두, 빠지면 지금의 기본값 규칙), `work[{task, summary, topics, task_type?}]` (새 업무는 task_type 필수), `problems[]`, `later_items[]`.
- 규칙 (지금 프롬프트에서 옮김): 자료 기준, 주제 정의(플랫폼·앱 이름 아님), 문제, 나중에 할 일.
- 상위 클래스(테마)는 다음 설계에서 여기에 붙인다.

### 합치기
- ①의 none → `rows[{task: null}]`, off → `rows[{task: "off"}]`.
- ②의 업무 정의와 배정 → `tasks`, `rows` (②의 off 도 `"off"`). 새 업무의 `task_type` 은 ③의 것.
- ③의 자료 여부·요약·주제·문제·나중에 할 일 → 같은 patch 의 `resource`, `work`, `problems`, `later_items`.
- 이유(`reason`)는 업무 행은 ②의 것, 나머지는 ①의 것.

## LangGraph 연결

- 의존성: `.package(url: "https://github.com/bsorrentino/LangGraph-Swift.git", revision: "d91c62aaa25e818f2667482c6edbe635a375ec45")`. 문서 플러그인을 브랜치로 물고 있어 버전 번호로는 받을 수 없어 커밋을 고정한다. MIT, swift-tools 5.10, macOS 13+. 마지막 커밋 2025-08-01 (v4 베타). 임시 패키지에서 빌드·재시도 고리·조건 분기를 확인했다.
- 단계 코드는 타입이 있는 구조체로 짠다: 단계마다 입력·출력 타입과 `run` 함수 하나. LangGraph 의 상태는 `[String: Any]` 이므로, 정해진 키에 타입 값을 넣고 꺼내는 연결 코드만 LangGraph 를 안다.
- 실행기는 프로토콜 뒤에 둔다: `LangGraphRunner` 가 구현한다. 라이브러리에 문제가 생기면 같은 프로토콜의 자체 실행기로 바꾸고 단계 코드는 그대로 둔다.
- 그래프 정의(노드·간선·조건)를 데이터로 한 곳에 둔다. 실행기와 흐름도 출력이 같은 정의를 읽는다. LangGraph-Swift 는 그래프 그리기를 지원하지 않으므로 Mermaid 는 우리가 만든다: `wgctl pipeline-graph`.

## 측정

- `wgctl gold-run --from YYYY-MM-DD --pipeline single|staged [--runs 2] [--model M] [--reasoning R] [--out FILE]`: 정답 세트의 배치를 `gold-candidates` 와 같은 방식으로 다시 만들어 고른 파이프라인으로 판정만 받는다 (기록 안 함). 행마다 판정을 `{"배치:행": 판정}` 으로 쓰고, `--runs 2` 면 두 실행 사이에 달라진 행 비율도 낸다. 판정은 앱처럼 검증해 앱이 거부할 판정은 실패한 배치로 센다.
- 채점은 `wgctl gold-score --predictions FILE` (업무 기준: 없음·업무 외 = 업무 아님, 그리고 둘을 구분한 엄격 점수).
- 같은 조건: 같은 재구성, 같은 후보 업무, 같은 모델(gpt-6-luna)과 추론 강도(medium).
- 성공 기준: (1) 3단계의 업무 기준 정확도 ≥ 한 번 호출, (2) 3단계의 흔들림 < 한 번 호출, (3) 배치당 호출 3번 이하 (빠진 행 재시도 제외).

## 앱 전환

- `BatchConfig.pipeline`: `.staged` (기본) | `.single`. 화면에는 드러내지 않고 숨은 설정값(UserDefaults)으로 바꾼다.
- 측정에서 성공 기준을 넘어 기본값을 `.staged` 로 바꿨다 (아래 측정 결과).
- 배치 기록: `llm_patch` 는 합친 patch, `raw_response` 는 단계별 원문을 담은 JSON, 프롬프트는 단계별로 구분해 이어 붙인다. 토큰 수는 합계.

## 실패 처리

- 단계 호출이 실패하면 지금처럼 배치 실패로 기록하고 백오프 뒤 다시 한다.
- 빠진 행은 그 단계를 빠진 행만으로 한 번 더 묻는다. 그래도 빠지면 배치 실패.
- ②가 모르는 업무 ref 를 쓰면 지금의 검증과 같이 배치 실패.

## 테스트

- 단계별 (가짜 LLM): ①이 모든 행을 셋으로 나눔, ②의 프롬프트에 work 행만 들어감, ③의 프롬프트에 업무별로 묶인 행이 들어감.
- 합치기: 세 단계 결과로 만든 patch 를 적용한 그래프가, 같은 판정을 한 번 호출 patch 로 적용한 그래프와 같다.
- 흐름: 빠진 행 재시도(첫 응답이 한 행을 빠뜨림 → 그 행만 다시 물음), 업무 행이 없으면 호출 1번, 보통 3번.
- 흐름도: Mermaid 출력에 노드와 간선이 모두 있다.

## 하지 않는 것

- 상위 클래스(테마): 다음 설계에서 ③에 추가한다.
- 단계마다 다른 모델·추론 강도: 측정 뒤에 정한다.
- 체크포인트 저장, 중단 후 재개.
- 로컬 판단 모델(Laya 등).

- 조건: 정답 세트를 만든 시각에 있던 업무만 후보로 넣는다. 요청 한도(HTTP 429)·서버 과부하는 기다렸다 그 배치를 다시 하고, 두 방식은 차례로 잰다. 판정은 앱처럼 검증해(빠진 행, 모르는 업무) 앱이 거부할 배치는 실패로 세고 그 행은 오답으로 친다.
- 한 번 호출에서 거부된 배치는 모두 업무를 정의하지 않고 업무 id 를 행에 바로 쓴 경우다 (`unknownTask`). 흔들림의 분모 531 은 두 실행 모두에서 받아들여진 행이다.
- 3단계는 마지막 검토 뒤 고친 판이다 (목록·null 답 해석, 후보 업무 id 를 바로 쓴 답, 정의하지 않은 ref 는 다시 묻기). 고치기 전, 앱 검증 없이 잰 값은 한 번 호출 83.9% / 95.3% 흔들림 14.9%, 3단계 90.1% / 95.6% 흔들림 1.6% 였다.
- 참고: 정답 세트를 만든 뒤 실 앱이 만든 취미 업무(EA FC 선수단 구성)를 후보에 그대로 두면 한 번 호출 47.3% / 51.8%, 3단계 67.2% / 49.2% 다 (고치기 전, 앱 검증 없음). 두 방식 모두 KFPL 행 389개 중 134~257개를 그 업무에 붙였다. 후보 목록에 취미 업무가 있으면 어느 방식도 취미 규칙을 지키지 못한다.
